Step 1 · Indexing (offline)
Knowledge base & chunking
Before any user ever queries the system, source documents are split into smaller, self-contained chunks. This entire indexing pipeline runs once, offline — not at query time.
Step 2 · Indexing (offline)
Embedding generation
Each chunk is passed through an embedding model (e.g. text-embedding-ada-002, BGE, Cohere) which converts it into a high-dimensional vector. Similar text → similar vectors.
Step 3 · Indexing (offline)
Vector database
All embeddings are stored in a vector database (Pinecone, Weaviate, Qdrant, pgvector) optimised for fast nearest-neighbour search. Indexing is now complete.
Step 4 · Runtime
Query processing
A user submits a query at runtime. It's passed through the same embedding model as the documents — so the query vector lives in the same semantic space and can be meaningfully compared.
Step 5 · Runtime
Similarity search & top-k retrieval
Cosine similarity scores the query vector against every stored chunk. The top-k most similar chunks (k = 2 here) are selected and passed forward — not the whole database.
Step 6 · Runtime
Augmented prompt & LLM generation
The retrieved chunks are combined with the user's query into an augmented prompt. The LLM generates a response grounded in this targeted context — not from parametric memory alone.
